# 0015: Fewer Approval Prompts Without Losing Consent

## Status

Accepted. Supersedes [ADR-003](../../ADR-003-bash-allowlist.md). Amends the per-Turn path memory in [ADR-002](../../ADR-002-approval-gated-access-beyond-project-root.md).

## Context

ADR-003 relaxed the bash rule but left two defaults that make the feature inert in practice. The Bash Allowlist ships **empty**, so a fresh install asks before every `bash` Tool Call — `ls`, `git status`, `cat`, a log tail, all of it. And an entry is matched against the first token only, so `git` as an entry also silences `git push`, while `git status` as an entry matches nothing. The safe setting is therefore either absent or dangerously broad, and most users never find it at all.

A dogfooding session made the cost concrete: asked to start a project with `docker compose up --build -d`, the agent collected a prompt for nearly every command it ran to get there — reading files, checking logs, listing containers — and the user approved each one on reflex. A prompt answered on reflex is worse than no prompt: it trains the user to say yes, which is exactly the state a consent mechanism must not produce. Meanwhile the prompts that *did* matter — a `.env` read, a destructive command — looked identical to the noise.

The obvious fix, "stop asking for things inside the Project Root", throws away the boundary ADR-002 and ADR-003 built. That boundary is not about where a command runs; it is about what a command can do. A build inside the Project Root writes files; a `docker compose down -v` inside the Project Root deletes volumes; a `cat .env` inside the Project Root exfiltrates a secret into the model's context. Location alone cannot separate `ls` from `rm -rf`.

The narrower fix is to make silence **earned and specific**. Three separate defects had to be addressed: the default was ask-everything, an approval could not be remembered, and the allowlist could not express "this subcommand but not its sibling".

## Decision

Silence is the default for read-only commands, and everything else asks once and can be granted for one exact command in one project.

- **Ship a default Bash Allowlist of read-only commands.** `ls`, `pwd`, `cat`, `head`, `tail`, `wc`, `rg`, `grep`, `find`, `git status`, `git diff`, `git log`, and `git show` run silently on a fresh install. The list deliberately excludes `echo` (it can redirect into a project file) and `git branch` (it deletes branches). An absent `silentBashCommands` means these defaults; an explicit `[]` means ask everything, preserving the old escape hatch; a non-empty list is the defaults plus the user's entries. Absent and empty are different values because they are different intents: "I have not configured this" versus "I want zero trust".
- **An allowlist entry is a command prefix, and chains are checked per segment.** A one-token entry behaves as before (`ls` matches `ls -la`); a multi-token entry matches a leading token sequence, so `git status` silences `git status --short` and says nothing about `git push`. The command is split on `;`, `&&`, `||`, `|`, and newlines, and **every** segment must independently qualify — `git status; rm -rf /` is not a Silent Bash Call. Backticks, `$(`, and `<(`, which cannot be split safely, disqualify the whole command. A redirection into a file (`>`, `>>`, `&>`) or a `tee` disqualifies it too: a reader that writes is not a reader, and the old rule — that a redirection only had to avoid Sensitive Paths — would have let `cat notes.md > src/app.ts` rewrite a project file silently. Descriptor duplication (`2>&1`) writes nothing and stays silent.
- **A Destructive Verb always asks, whatever the allowlist says.** Any segment containing `rm`, `rmdir`, `dd`, `mkfs`, `shutdown`, `reboot`, `kill`, `pkill`, `killall`, `chmod`, `chown`, `sudo`, `su`, a `find` execution flag (`-exec`, `-execdir`, `-ok`, `-okdir`, `-delete`), a `git push`/`git reset --hard`/`git clean`, or a package `publish` asks for approval. This closes the hole prefix matching would otherwise widen: `find . -exec rm {} \;` starts with an allowlisted token, and without this rule it would run silently.
- **An Approval Grant is consent attached to one exact command in one project.** Pressing `a` on the Approval Prompt persists the whitespace-normalized command — `docker compose up --build -d`, not `docker compose` — so `docker compose down -v` asks separately. Grants live in `~/.vicode/trust.json`, keyed by resolved Project Root, **never** in `.vicode.json`: that file is committed, and a grant written there would travel to everyone who clones the repo, letting a project grant itself permission. A grant silences its exact command despite the Allowlist and the Destructive Verbs, because it is a deliberate per-command decision; it does not bypass the working-directory guard, which asks about a location the grant does not name.
- **An approved path lives for the Session, not the Turn.** ADR-002's per-Turn memory expired too fast to matter: the same out-of-root file or `.env` prompted again on the very next message. An approved resolved path now holds until the Session changes — a new Session, a resumed one, or a switch — and is never written to disk. Secret access is re-granted deliberately rather than inherited by a later run.
- **The Approval Prompt becomes a decision, not a payload.** It offers a highlighted menu — Approve once, Always approve this command (bash only, where "always" means something beyond the Session), and Reject — navigated with `↑`/`↓` and confirmed with `Enter`. Defaulting the highlight to Approve once keeps Enter on the reversible answer, and offering no single-key shortcuts keeps a reflexive keystroke from granting persistence. A bash call renders its command on one line instead of dumping JSON, so the thing being approved is legible at a glance.
- **`/permissions` lists and revokes.** A persisted grant with no revoke surface is a trap, so `/permissions` shows this project's Command Grants and the Session's approved paths, and `Ctrl+D` removes the highlighted row.

## Consequences

- **Positive**: `ls`, `git status`, `rg`, reading a log, and the rest of the read-only vocabulary stop interrupting the user on a fresh install — the prompts that remain are the ones that change something or reach a secret.
- **Positive**: chains and Destructive Verbs mean widening the allowlist no longer widens what can run silently. `git status` is safe to ship precisely because `git push` is out of its reach.
- **Positive**: the reflex-approval failure mode is addressed at its source. A user who sees `docker compose up --build -d` once, presses `a`, and never sees it again has actually read it; a user who presses `y` twenty times has not.
- **Negative**: a default allowlist is a compiled-in security opinion, and every entry is a small bet that its command has no destructive mode the Destructive Verb scan misses. `find` is the riskiest of the set; its execution flags are scanned, but a future flag could slip through. The list is therefore read-only by construction, not by trust in each program's flags.
- **Negative**: exact-command grants prompt again for trivial variants — `docker compose up --build -d` granted is not `docker compose up --build` granted, and a command piped into `tail` is a different string. This is the same trade ADR-0013 made for URLs, and the same answer: consent is for what was asked.
- **Negative**: `~/.vicode/trust.json` is a second global state file, and it is invisible to version control and to teammates. Grants are per machine and per project, and a revoke is local.
- **Negative**: the Destructive Verb list is a heuristic that will occasionally ask about a harmless command (`git log --grep rm`). The failure is a prompt, not a block, so the cost is one keystroke; the opposite failure — silence on a destructive command — is unrecoverable.
