# 0013: Outbound Fetch Is Approval-Gated

## Status

Accepted

## Context

Issue #90 asked for two Tools: `web_search`, which shipped under issue #93 and is recorded in ADR-0012, and `web_fetch`, which retrieves a page and hands the model prose it can read. Both are read-only — neither writes anything to disk — and both leave the machine. Issue #95 asks for the three decisions the pair rests on to be written down together, because none of them is derivable from the code: where a network credential lives, why its absence does not gate the chat, and what gates an outbound request.

Two of the three were decided with `web_search` and recorded in ADR-0012: a network credential is not a Provider credential, and a missing one is not a pre-chat gate. They are restated below so the three stand in one place for a reader arriving from either Tool; ADR-0012 remains the record of their full reasoning, and this ADR defers to it rather than competing with it.

The third was new with `web_fetch`. The Approval Rule already had two ways to stop a Tool Call: a target that is a Sensitive Path, and a target outside the Project Root. Both are about an act *on this machine* — material already on disk that the user has not consented to reach or to change. `web_fetch` is a different act: it issues a request to an arbitrary host, chosen by the model rather than the user, and the answer comes back into the conversation.

The Tool writes nothing, so `dangerous` — the mark that has always driven approval — stays false, and a Tool that is not dangerous runs unasked. That left two tempting answers, and each is wrong in a different way. Mark it `dangerous` anyway and the flag starts meaning "may leave the machine" as well as "may wreck the project", so the next reader cannot tell which of the two a `dangerous` mark is warning about. Let it run, because it writes nothing, and a local read inside the Project Root and a request to a stranger's host become the same kind of act because both are reads. Neither answer states the reason a fetch is different — that the host is the model's choice rather than the user's — so the choice would have been made by default rather than by argument, which is how an unsettled judgement ends up recorded as an accident.

## Decision

- **A network credential lives outside the Provider concept.** A Search Credential — the name CONTEXT.md and GLOSSARY.md give it — authenticates a service the agent asks a question of; it is not a route the user chats through, so it is never selectable as a route, and it never appears in the Route Label or in cost accounting. Recorded in full in ADR-0012, and stated here because the two decisions that follow both rest on it: were the credential a Provider's, it would be a route, it would carry a `/key` screen, and it would be owed a gate.
- **A missing search credential is not a pre-chat gate, while a missing Provider key is.** A Provider key gates because there is no route to chat through without one — the API Key Entry Screen's required mode exists for exactly that case. A Search Credential authenticates a service that is not a route, so with it absent every route still works and ViCode is fully usable without web search; the absence is reported at the moment `web_search` is called, naming the credential and how to set it. Gating the chat on a Tool the user may never call would make the app depend on a feature it does not need. The reasoning is ADR-0012's; the two decisions are one argument, not two.
- **An outbound fetch is Approval-gated, and that is a judgement call rather than a settled fact.** A `web_fetch` Tool Call pauses for the user, showing the URL, before any request is issued — unless that exact URL was already approved during the current Turn, so a multi-page investigation asks once per URL instead of once per call. Approval attaches to the exact URL, not to the host: approving one URL on `example.com` approves nothing else on it. `dangerous` stays false, because the flag's content is what a call can wreck on disk and this Tool writes nothing; the pause is carried by this Approval Rule instead. The reasoning is that a local read inside the Project Root and a request to an arbitrary host on the model's say-so are not the same kind of act, whatever they have in common as reads: the target of a file operation is the user's project, chosen by a model working inside it, while the target of a fetch is a host the user has never named. This is a judgement call, not a settled fact — a fetch is read-only, and wanting unattended multi-page research is a legitimate position to hold. What tips the line is that the host is the model's choice rather than the user's, and that the response re-enters the context. Approving a host at a time, or trusting a read-only fetch outright, would be a defensible reversal; this is where the line currently stands.

## Consequences

- **Positive**: all three decisions live in one place, and both glossary entries that name them — **Search Credential** and **Outbound Fetch Approval Rule** — point at this ADR, so a reader who meets either term in CONTEXT.md lands on the reasoning instead of having to infer it from code that only shows the outcome.
- **Positive**: the Approval Rule keeps one shape — three cases, one mechanism — rather than growing a second gate for a Tool that writes nothing. Each case keeps its own memory: a resolved path for the rest of the Turn, an approved URL for the rest of the Turn, and none at all for `bash`.
- **Positive**: `dangerous` keeps its meaning, so it can still be read as "this call can change the project" instead of the vaguer "this call does something someone might object to". The approval is legible as an Approval Rule, in the same place and the same words as the path rules it sits beside.
- **Negative**: approving the exact URL means the same page reached with a different query or fragment asks again. That is the cost of approving what was actually requested rather than a host the model can then roam freely, and it is the same trade the per-Path rule already made.
- **Negative**: research that touches many URLs carries more prompts than a filesystem-heavy session, at least until each URL has been approved once in the Turn. The alternative — blanket trust or per-host approval — buys fewer prompts with consent given before the model has named a target.
- **Negative**: two of the three decisions are now written down twice, in ADR-0012 and here. The duplication is deliberate and one-directional: ADR-0012 carries the reasoning and this ADR defers to it, so the two statements must be edited together — a divergence between them would be a second reading of a rule that ADR-0011 exists to prevent.
